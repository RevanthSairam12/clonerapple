# Part 1 — Configurable shipping

## Context
The user requested Part 1 of `paymentprocessplan.md`: staff-configurable shipping charge and free-shipping threshold, consistent cart/checkout totals, authoritative PayU calculation, and immutable historical shipping on orders. Parts 2–6 are deferred; document only a brief baseline and outstanding questions for those parts, not implementation or claims of full verification.

- Preserve all existing unrelated working-tree changes. Do not stage them or promise a clean repository by discarding them.
- After plan approval, create `CHECKOUT_PLAN.md` first, recording findings, decisions, deferred scope and test plan.

## Verified findings
- `src/lib/checkout/shipping-rules.ts` already has a pure quote function, but chooses the first active method and combines its threshold with Orders → `free_shipping_over`. Legacy zero means disabled threshold.
- `src/lib/checkout/settings.ts` reads settings/methods outside any caller transaction. Initiate resolves catalogue prices and shipping before `createOrderUsing()` opens the stock/coupon transaction (`src/lib/payu/orders.ts`).
- The expected-total check is nested inside coupon processing; `CheckoutForm` sends it only with a coupon and ignores totals returned with a 409. Shipping-only changes are therefore not consistently guarded.
- Shared `parseRupeesToPaise` / `formatRupees` exist in `src/lib/store-admin/money.ts`. Settings descriptors carry field help; there is no separate `check-field-help` script. Generic number validation cannot preserve blank thresholds or parse decimal rupees correctly.
- Notifications currently infer shipping from total minus items and thus understate it when discounts apply (`src/lib/notifications/order-context.ts`). Existing documents mostly read stored shipping correctly. Preserve that historical-snapshot behavior rather than recomputing orders with current settings.
- The current settings API has origin/role checks and best-effort auditing after save. Shipping changes need an actual audit row, not an unsupported claim that the current audit is atomic.
- Migration files currently end at 0046; recheck before allocating 0047. No live settings or applied-migration query has been performed during planning.
- Existing fixture patterns can copy public serial-sequence defaults. New/extended DB fixtures must use isolated local sequences and exercise actual database transactions, not skip them.
- Existing notification readiness is documented as configuration-blocked. Preserve that distinction from test/code correctness and never claim all checks pass if they do not.

## User decisions (answered)
1. Two canonical fields in Settings → Shipping are the only shipping rule; retain legacy method records labeled unused for checkout.
2. Compare the sale-priced item subtotal BEFORE coupon discount.
3. Empty threshold means no threshold-based free shipping: always charge, unless disabled or a valid free-shipping coupon applies. A zero charge means free.
4. Preserve effective existing settings during cutover; ₹50/₹999 are acceptance-test examples, not an authorized change to live rates.

## Implementation outline
1. **Document first:** create `CHECKOUT_PLAN.md` with the above findings and user answers, baseline-only notes for deferred Parts 2–6, rollout precautions and evidence slots. Do not claim all six parts were fully investigated.
2. **Canonical policy/settings:** evolve `shipping-rules.ts` rather than duplicate it. Use enabled, integer-paise standard charge and nullable integer-paise threshold. Compare pre-coupon sale subtotal; a validated free-shipping coupon forces zero. Explicit zero threshold means every nonempty cart meets it; legacy zero thresholds map to null. Move the switch and new rupee inputs to Settings → Shipping, preserve courier/tracking controls, remove the obsolete pricing inputs from Orders, label retained methods as unused. Add plain validation, descriptor help and a live example line. Reuse shared money parsing/formatting.
3. **Preserve configuration:** add a dry-run-first, explicitly applied, idempotent settings backfill script using the existing JavaScript selector—not a SQL approximation of `localeCompare`. Copy the selected method's rate (or zero without an active method) and the minimum positive global/method threshold (or blank), preserving disabled-store configuration. Under one locked transaction (serializing against legacy settings/method writers) create both canonical keys and a privacy-safe `writeAudit` row; never overwrite existing canonical values or modify order rows. Reject partially initialized pairs rather than inventing a missing value. Re-read under the lock during apply so stale dry-run values are not copied. Existing `store_settings` storage is sufficient: no schema/RLS migration is necessary unless implementation discovers a concrete need. Run the dry-run and verify parity before applying and activating the canonical reader; configured deployments missing the pair must fail closed with a clear initialization error, not silently use zero defaults. Retain legacy records unchanged and label their rates unused after cutover.
4. **Transactional authority:** add transaction-aware settings/catalogue readers and use them inside the existing order/stock/coupon transaction. Resolve sale state from the database clock, compute all amounts and the final pricing snapshot there, and keep stock and coupon lifecycle behavior unchanged. Always compare the optional displayed total and advisory unit prices against the resolved transaction quote. Return one consistent 409 payload containing new items and totals before committing any order/stock/coupon side effects. Generate the PayU amount/hash only from the committed server total. Preserve POS and callback verification paths unchanged.
5. **Storefront consistency:** use the same pure quote helper and integer-paise catalogue amounts in cart/bag/checkout. Show Subtotal, applicable Discount, Shipping and Total plus the short amount-to-free-shipping nudge. Invalidate stale coupon totals on quantity, price, policy or code changes, bind asynchronous responses to the captured request signature and reject obsolete responses immediately. Refresh at sale transitions/on return to the page without aggressive polling or exceeding coupon limits. A pre-Pay coupon refresh that changes the previously displayed total must require review, not silently replace the expectation. Consume both items and totals in every 409 response, including direct-buy state rather than only updating bag storage. No silent free quote when configured settings cannot be read; disable payment with a useful unavailable state.
6. **Historical surfaces:** success, account order/receipt, admin order/invoice, packing slip, notifications and exports use the order's stored shipping, never current policy. Fix notification subtraction; expose a stored shipping line (including Free) where missing. On packing slips add only the requested shipping line, leaving item prices omitted and updating the explanatory copy. Keep report revenue definitions unchanged; verify stored totals include shipping and item revenue excludes it.
7. **Auditing/revalidation:** preserve role/origin guards and use existing `writeAudit(input, tx)` within shipping writes; throw if it returns false so a change cannot commit without its audit. Keep audit payloads limited to nonpersonal settings. Invalidate relevant paths/tags after commit, using immediate expiry if tags are used. Add no new RLS changes to existing tables.
8. **Scoped commits/docs:** make small shipping-only commits for policy/settings, transactional totals, then display/regressions/docs. Add the shipping section and real evidence to `FEATURES.md`, staging only this task's changes because it is already dirty. List all changed storefront files and any new routes/APIs. Leave unrelated user edits untouched and explain the resulting non-clean status.
