### 1.4 Major limitations

1. **No runtime verification.** No server was running (`http://localhost:3000/` refused connection) and I did not start one, because doing so writes to `.next/`. Public reachability of `public/sites.original-backup/**` is therefore asserted from Next.js's documented public-directory semantics, not observed over HTTP. Confidence: **highly likely**, not confirmed.
2. **No database access.** The live CMS rows (`apple.hero_tiles`, `apple.footer`, etc.) were **not** read. What renders on the deployed site may differ from the code defaults. `scripts/inspect-apple-keys.mjs` exists and performs read-only SELECTs; running it needs your approval.
3. **No build or typecheck** was executed (both write files). No claim is made that the project currently builds.
4. **No visual comparison against live apple.com.** Image provenance below rests on filenames, provenance-admitting code comments, directory structure, and my own visual reading of 6 images — not on side-by-side comparison with a captured Apple page.
5. **Not exhaustive.** `src/app` route pages outside the homepage and edu store were not read line-by-line; findings there are limited to what the full-text searches surfaced.

### 1.5 Preliminary launch-risk assessment

**Assessment: not launch-ready in the current state, primarily on asset-provenance grounds rather than design grounds.**

Reasoning:

- The repository documents its own provenance. `src/components/sites/www-apple-com-736d3707/root-8a5edab2/data/tiles.ts:1-2` states the content is *"GENERATED … Content is verbatim from https://www.apple.com/ (captured 2026-08-20)."* `icons.tsx:1-2` says the same for its SVG paths. `README.md:60-63` states the assets *"were downloaded from apple.com and remain © Apple Inc."* and that *"the assets aren't licensed for redistribution or commercial use. Swap them for your own before publishing anything."* This is not inference — it is the project's own written record.
- A substantial de-brand pass has already been done and is **staged** (273 entries): Apple's logo wordmark paths are emptied, the Apple Music/Arcade/Fitness+ wordmarks are removed, the entertainment gallery arrays are emptied, the Apple Card promo tile is deleted, apple.com destinations are rewritten to internal routes, and the locale banner/nav/footer/ribbon copy is rewritten in Gadzio's own words. That work is real and should be preserved, not undone.
- What remains is concentrated and identifiable: **asset binaries** (which the de-brand pass deliberately did not touch) and a smaller set of **verbatim text, SVG path data and slogans**.
- The single highest-leverage action is replacing the image/video/font binaries with licensed or original equivalents. Everything else is smaller in volume.
- This is a technical and evidentiary assessment only. It is **not** a legal opinion, and it does not assert that any particular claim would or would not succeed. See Section 14.

## Section 9 — Public exposure and unused files

### 9.1 The backup directory (exposure, not copyright)

`public/sites.original-backup/` — 321 tracked files, 9.3 MB of assets. Next.js serves everything under `public/` at the web root, and the folder name has no leading dot, so `https://<host>/sites.original-backup/www-apple-com-736d3707/root-8a5edab2/images/tiles/hero_macbook_air_m5__eb1idggd120y_large_2x.jpg` resolves. **Confidence: highly likely** (Next.js public-directory semantics). **Not HTTP-verified** — no server was running.

Two distinct concerns:
- **Exposure:** the backup makes every Apple original — including the Apple Card logo artwork and the SF Pro fonts — individually retrievable. A reviewer, journalist or rights-holder can enumerate it without touching the app.
- **Copyright:** the same files are a distribution act regardless of whether anyone fetches them.

These are separate findings and should be remediated together but reasoned about separately.

Also note: the backup is **redundant with version control**. Every file is tracked in Git (321 entries), so deleting the working copy does not lose history — it remains recoverable from the repository.

### 9.2 Unused files (review, do not delete blindly)

168 of the 218 live Apple-directory files are unreferenced by code, and 266 of 321 backup files are. But "unreferenced" ≠ "unreachable": `public/` files are directly addressable by URL. Before deleting, note also that the admin media library (`src/app/api/admin/media/**`, `src/lib/admin/storage.ts`) uses Supabase Storage rather than `public/`, so these files are not admin-managed.

### 9.3 Dynamically constructed paths

One dynamic pattern exists and was traced: `AccessoryDetailPage.tsx:112` builds `` `/in/shop/iphone/accessories/${product.categorySlug}` `` from the catalog; `data/types.ts:71-76` supplies six fixed `ACCESSORY_NAV` slugs. No Apple *asset* path is built dynamically — all asset references are literal strings, so the reference trace in Section 3.2 is reliable.

### 9.4 Broken / missing assets

The staged `tiles.ts` blob references ten `hero_macbook_air_m5__eb1idggd120y_*` files that are **absent from the live tree** (present only in the backup). If those 72 lines are ever restored without also restoring/patching the images, the hero renders broken. No other broken asset paths were found among the referenced set.

### 9.5 Source exposure

`public/sites/www-apple-com-736d3707/root-8a5edab2/images/tiles/GENERATE-ASSETS.JS` (SRC-01) is a first-party `sharp` batch-resize utility sitting inside a publicly served directory. It is generic code containing no secrets or Apple IP, but a build utility does not belong on a public web path. **Hygiene finding, not a rights finding.** No credentials, API keys, tokens or `.env*` content is exposed by the `public/` tree (`.env*` is gitignored at `.gitignore:7` and lives outside `public/`).

## Section 14 — Limitations and legal caveat

**This report is a technical and evidentiary audit. It is not legal advice, and it does not reach legal conclusions.**

Specifically:

- Nothing here asserts that any element **infringes** copyright, trademark, design right, or any other right, nor that Apple (or OPPO, or any other party) would or would not have a **valid claim**. That determination depends on facts and law outside this analysis — including registrations and their scope, jurisdiction (this appears to be an India-facing storefront), whether particular uses qualify as nominative or descriptive fair use, the originality threshold applicable to particular design elements, and applicable limitation periods.
- Confidence labels (**confirmed / highly likely / possible / unverified**) describe the strength of *technical provenance evidence* — filenames, directory structure, code comments, and visual inspection. They are not statements about legal status. "Confirmed Apple origin" means *the technical evidence that this file came from Apple's site is strong*, not *this use is unlawful*.
- Section 7 deliberately **avoids** concluding that any design element is protectable or infringing. Design conventions shared across e-commerce (grid layouts, product cards, cart flows, search patterns) are generally not protectable, and this report recommends against changes based on similarity alone. Where it flags category C items, the recommendation is the *smallest* differentiating change, not a redesign.
- The audit deliberately **preserves** legitimate factual use of Apple marks (Section 10). Naming a genuine product accurately is different from reproducing Apple's marketing expression, and this report treats them differently.
- **Legal review by qualified counsel is required before acting on any item**, particularly R-003, R-005, R-012, R-014 and R-022. Item **R-012** (a non-affiliation and trademark notice) is the one recommendation with the clearest non-technical benefit and can be implemented independently of all others.
- The audit was **not exhaustive** of the repository, was **not** validated against a running instance of the site, and did **not** read the live database. Section 13.4 lists every unverified claim. If the repository changes after 2026-10-11, or if the CMS rows differ from the code defaults, findings must be re-derived rather than assumed to still hold.

**No changes in this report are authorised for implementation. Approval must be obtained in a later conversation before any remediation.**
